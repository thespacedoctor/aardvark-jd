# Mutating commands hand sync to a detached process

Every mutating command mirrors the tree out to Google Drive, Todoist and craft.do before returning, and measurement put `av add_project` at **30.7 s** against a 500 ms target — 29.9 s of it network, across four services in a fixed order, with no single dominant offender left to optimise away. So the seven mutating commands (`add_project`, `add_area`, `add_category`, `add_id`, `set_emoji`, `repair_emoji`, `archive`) now do their local work, spawn `av craft_sync` in a new session, and exit. The explicit `*_sync` and `connect_*` commands stay in the foreground, and `--wait` forces the foreground path on any command.

## Considered options

- **Make sync faster instead.** Already done as far as it goes, and it is not close. Index-content comparison cut craft from 118 API calls to 41 and stopped the rate-limit failures; an OR-ed `files.list` per tree level would cut Drive from 45 calls to about 5. Together those take the command to roughly 19.8 s. The floor is set by sequential round trips to four services, not by call counts, so no further optimisation reaches 500 ms while the command waits.
- **A launchd agent.** Survives reboots and could run unattended repair syncs, but it is macOS-only, needs an install and uninstall surface, and is a large commitment to make before the drift marker has shown whether unattended retry is even needed. Left as the upgrade path.
- **Drain the queue on the next invocation.** No background process at all: record that a sync is due and let the next `av` command do it first. Rejected because it relocates the 20 seconds onto an unrelated later command, and leaves the mirrors stale for as long as the CLI goes unused.

## Consequences

- **The carrier is the existing repair sync, not new code.** `av craft_sync` already runs `gdrive -> todoist -> craft` in the mandated order, so backgrounding is one spawn of a command that already exists. This is also why scoped incremental syncing was ruled out of scope: with a whole-tree repair sync doing the work off the critical path, scoping buys only a faster background job.
- **Ticket 08's concurrency contract survives intact, and WAL stays declined.** At most one sync runs at a time, held by a lockfile beside `aardvark.db` inside `00_INDEX🗂️` (per-system by construction, and per-machine for free because that directory is Dropbox-ignored). A mutation arriving while a sync runs sets a pending flag rather than starting a second writer; the running sync re-checks the flag on completion and goes round again. A whole-tree repair subsumes every mutation made during the previous run, so the loop drains as soon as the user stops typing.
- **Failure is no longer visible at the terminal**, because the process that would have reported it has exited. This is less of a change than it appears — sync failures were already downgraded to warnings, since the filesystem and SQLite mutation has already succeeded and remains the source of truth. What is new is that they must be *recorded*: a per-mirror drift marker in the index carries each mirror's last success and last failure, `browse` renders it, and the next command prints a one-line warning if the last sync failed.
- **A stale lock is the worst available failure**, because it would stop syncing silently and permanently. The lockfile therefore carries a pid and a start time, and is treated as stale when the pid is gone, with an age cutoff as a backstop against pid reuse.
- **`av add_project --wait` exits non-zero when a mirror fails.** That does not mean the command failed: the folder, the index row and the Johnny Decimal code all exist. It means the entity was created and a mirror did not sync, which is the condition a script chaining onto a craft URL needs to branch on.

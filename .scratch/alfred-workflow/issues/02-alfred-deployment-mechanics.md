# How does a workflow get from a repo directory into Alfred, and stay linked to it?

Type: research
Status: resolved
Findings: ../research/02-alfred-deployment-mechanics.md

## Question

The workflow's source of truth is a directory inside the aardvark-jd repo, but Alfred keeps workflows in `user.workflow.<UUID>` directories inside its preferences folder — here `/Users/Dave/Dropbox/Apps/alfred/Alfred.alfredpreferences/workflows/`, which is itself inside Dropbox. Establish how those two are connected without hand-copying files.

Find out and write up:

- **Whether Alfred tolerates a symlinked workflow directory.** If `user.workflow.<UUID>` is a symlink to the repo directory, does Alfred load it, and does it keep working across an Alfred restart and a preferences sync? If not, what is the supported alternative — a symlinked preferences folder, a copy step, something else?
- **Whether the UUID directory name matters.** Is it generated by Alfred on import, does it have to match anything inside `info.plist` (`bundleid`, or an internal UID), and can a workflow be installed by creating the directory directly rather than by importing a file?
- **What Alfred rewrites, and when.** If the workflow is edited in Alfred's UI, what does Alfred write back to `info.plist` — reformatting, reordered keys, regenerated UIDs, absolute paths, cached state? This is the input to ticket 04's decision about whether the plist can be version-controlled directly.
- **The `.alfredworkflow` export format.** What it actually is, whether it can be produced from a directory by a script (so the repo's exported copy can be regenerated as part of a release rather than by hand), and how installing one behaves when a workflow with the same bundle id already exists.
- **Locating the preferences folder programmatically.** Confirm that the `current` key in `~/Library/Application Support/Alfred/prefs.json` is the supported way to find it — it is what resolves correctly on this machine — and what to do when Alfred is not installed or the key is absent.
- **Setting a workflow configuration variable from outside Alfred.** Whether an installer can write a user-facing configuration value into a workflow's storage without the user opening Alfred's preferences, and where that value is stored.

Where the documentation is silent, the 88 installed workflows are worked examples, and several of them are known to be maintained in public repositories that may show the pattern.

## Answer (2026-09-03)

Full findings: [research/02-alfred-deployment-mechanics.md](../research/02-alfred-deployment-mechanics.md). The Alfred preferences folder was deliberately not modified during this investigation, which is why two questions remain open at the bottom.

**The facts that change the design:**

- **The `user.workflow.<UUID>` directory name is arbitrary and means nothing.** Six of the 88 installed workflows are not named that way at all (`Google Suggest`, `Kill Process`, `markdust`, `picaxe`, `URL Encode-Decode`, `zettelkasten`), all enabled and loading. Grepping all 86 `info.plist` files for the string `user.workflow` returns zero hits: no workflow references its own directory name. Alfred's scripting dictionary confirms the directory name **is** the workflow UID — `reload workflow` takes "The UID (folder name), or the Bundle ID". So `install_alfred` should create a stable, legible `workflows/aardvark-jd` rather than minting a UUID.
- **Alfred does not gratuitously rewrite `info.plist`.** Five `alfredapp`-authored workflows were fetched from GitHub at the exact tag matching the installed version; two of them — `google-suggest` 2023.1 and `snippet-transformer` 2023.2 — are **byte-for-byte identical** to the file the vendor committed, after import and use. Alfred's own team commits `Workflow/info.plist` verbatim. This is a strong green light for committing the plist rather than generating it.
- **What Alfred does rewrite when a workflow is edited** is narrow and semantic, not cosmetic. The `amazon-suggest` diff had exactly two semantic changes and zero formatting noise: the **`objects` array was reordered** (identical contents, different order), plus `uidata` (per-node canvas coordinates) and the top-level `disabled` flag. The reordering is the churn risk — a nudge on the canvas can reshuffle it into a large meaningless diff. The canonical form is consistent across all 86 files: XML plist, tab-indented, keys strictly alphabetical at every level. No absolute paths are injected.
- **`.alfredworkflow` is a zip**, asserted by Alfred's own UTI declaration (`com.runningwithcrayons.alfred.workflow` conforms to `public.zip-archive`), and unzipping one into the workflows folder loads it. A scripted export must additionally strip `category`, honour `variablesdontexport`, and exclude `prefs.plist` and `.git`.
- **Configuration variables can be set from outside Alfred, supported.** Defaults live in `info.plist`, changed values in `prefs.plist` (which the documentation says to gitignore), written lazily — only 1 of the 34 workflows declaring `userconfigurationconfig` has one. The supported external write is the AppleScript `set configuration "<var>" to value "<v>" in workflow "<bundleid>"`, which persists to `prefs.plist` and takes effect immediately. Direct file writes work but Alfred does not hot-reload them; `reload workflow` forces it.
- **`prefs.json` → `current` is correct**, though undocumented. It is what `resolve-alfred-prefs` (behind `alfred-link` and `alfy`) reads first, and it is corroborated by `defaults read com.runningwithcrayons.Alfred-Preferences syncfolder`.

**One trap worth the whole ticket:** `~/Library/Application Support/Alfred/Alfred.alfredpreferences` also exists on this machine, but it is a vestigial shell containing only `preferences/local/`. An installer that falls back to the default path when `prefs.json` cannot be read would write somewhere Alfred never looks, and would appear to succeed. **The fallback must be a hard failure**, not a default path.

**Not settled, and deliberately so:**

- **Whether Alfred follows a symlinked workflow directory is untested.** It is community practice with no first-party statement in either direction, and testing it meant writing into the live preferences folder, which was outside this ticket's write scope. Both research tickets flagged it independently. It is now [Verify what Alfred writes, and whether it follows a symlink](14-verify-alfred-write-behaviour.md).
- **The preferences folder is inside Dropbox `/Apps/`**, which Alfred explicitly excludes from its own sync picker and advises against using ("at your own risk", "preferences not saving correctly"). This is pre-existing and not caused by this effort, but it means a symlink experiment may fail for that reason rather than for Alfred's.
- **An unresolved anomaly**: a `userconfigurationconfig` *default* inside `info.plist` was found rewritten (`com.au` to `co.uk`) on a workflow with no `prefs.plist`. If Alfred's import-time configuration sheet writes defaults back into `info.plist`, that dirties the version-controlled file and undercuts the green light above. Also folded into ticket 14.
- **A cheaper way out of the symlink question**: since the real logic lives in `aardvark_jd/alfred/`, the workflow directory may contain little beyond `info.plist` — in which case only that one file needs to be live, and the symlinked-directory question largely evaporates.

# Map: Alfred workflow for the aardvark CLI

Label: `wayfinder:map`

## Destination

A decided, ready-to-build specification for an Alfred 5 workflow that drives the `aardvark` CLI from the keyboard: which commands it surfaces, how each one is entered and confirmed, what the CLI has to grow to support it, and how the workflow is installed and kept current. The destination is a spec to hand to TDD implementation, not the implementation itself.

Two deliberate exceptions carry real code into the map, both because the decisions genuinely cannot be made on paper: the prototype tickets produce runnable Alfred workflow fragments so the interaction can be felt before it is locked, and the measurement they take is the input to the decision. Everything else is planning.

## Notes

**Domain.** `aardvark-jd` is a Python CLI (`aardvark` / `av`, same entry point) implementing a PARA + Johnny Decimal filing system over a folder tree, indexed in SQLite, mirrored out to craft.do, Todoist, Google Drive and Dropbox. Repo: `~/git_repos/_packages_/python/aardvark-jd`, branch `feature/cd-command` at charting time. See `CONTEXT.md` for the glossary this effort extends.

**Skills every session should consult.** `mattpocock-skills:grilling` and `mattpocock-skills:domain-modeling` for decision tickets; `mattpocock-skills:research` for research tickets; `mattpocock-skills:prototype` for prototype tickets.

**Standing preferences for this effort.** UK English. No mid-sentence line breaks in Markdown. Comments in source are UPPERCASE. Immutability by default. A short plan and explicit approval before non-trivial implementation. Implementation, when it happens, follows the user's global TDD rules (test-first, 80 per cent coverage) and Gitflow.

**Research findings** are written to `.scratch/alfred-workflow/research/` on the current branch rather than to throwaway `research/<name>` branches, because this repo's Gitflow rules require a branch name to be proposed before it is created.

### Settled while charting (2026-09-03)

These are foundational choices made during the charting grilling. They are premises for the tickets below, not tickets themselves.

- **Destination is a spec.** Prototypes produce runnable fragments; the build proper is a focused session after the map closes.
- **The workflow lives inside the aardvark-jd repo**, in a directory such as `alfred/`, shipped with the package. **Corrected 2026-09-04 by ticket 10**: not at the repo root — `MANIFEST.in` excludes everything outside `aardvark_jd/` and `package-data` ships only `aardvark_jd = ["resources/**/*"]`, so a top-level `alfred/` would ship in neither the sdist nor the wheel. It lives at **`aardvark_jd/resources/alfred/`**, located at runtime by `importlib.resources.files("aardvark_jd")`, which resolves identically in a checkout and in site-packages. It is a thin skin over the CLI and version-drifts with the CLI's command surface, so it belongs in the same repo at the same commit. Alfred's `user.workflow.<UUID>` directory gets pointed at the repo copy for live editing.
- **Command scope.** In scope: the read/navigate commands (`fd`, `open`, `cd`), the sync commands (`craft_sync`, `todoist_sync`, `gdrive_sync`, `repair_emoji`), and the mutating commands (`add_area`, `add_category`, `add_id`, `add_project`, `archive`, `set_emoji`). Out of scope: the setup commands, which are one-time and browser-interactive.
- **Alfred owns the interaction.** Every CLI prompt has a suppressing flag (`-e`, `-t`, `-y`, `-w`), so the CLI runs headless and Alfred replicates the prompts it needs in its own UI. No handing off to a terminal to finish a command.
- **One keyword.** A single `av` keyword with script-filter drill-down, rather than a keyword per command. `av` is free across the user's 88 installed workflows; `fd` and `open` are both already taken by other workflows, which rules out the obvious direct-keyword names.
- **The workflow finds the binary via the CLI itself.** A new `aardvark install_alfred` command deploys the workflow and bakes in the interpreter path it is running from (the CLI knows its own `sys.executable`; nothing else can answer this without guessing). A workflow configuration variable is the manual override. **Corrected 2026-09-04 by ticket 12**: what is stored is the **`aardvark` console-script path**, not `sys.executable` — there is no `__main__.py`, so the interpreter alone cannot launch anything, whereas the console script's shebang resolves its own interpreter with no environment activation. `sys.executable` is how `install_alfred` derives the path (`Path(sys.executable).parent / "aardvark"`), not what it writes. It is written to a per-machine plain-text pointer file outside Dropbox, because the workflow directory syncs and the configuration variable therefore cannot hold per-machine state.
- **Install is two-track.** `install_alfred` for the author: a live link to the repo copy, so repo edits take effect immediately. An exported `.alfredworkflow` committed to the repo for anyone installing the package from PyPI or conda. **Revised 2026-09-04 by ticket 10**: `install_alfred` is not author-only, because ticket 12's per-machine pointer file has to be written on every machine including one that installed by double-clicking the bundle. The command splits into two jobs — always write the pointer, and deploy the workflow unless one is already installed by another route. The install is editable here, so `importlib.resources` points at the repo for the author and at site-packages for a package user through one code path, which means the symlink serves both and there is no copy mode.
- **Script filters are fed by a new `--json` output mode on the CLI**, not by parsing human-readable stdout and not by importing `aardvark_jd.db` from the workflow. Measured: `aardvark fd` returns the whole tree in 240 ms cold, where `import aardvark_jd.db` alone costs 460 ms, so shelling out is both faster and less coupled. The JSON covers the read commands and the mutating commands' result objects (so Alfred can report what happened and reveal the new folder), and it must carry every per-entity mirror URL rather than just firing them.
- **Multi-argument entry is a hybrid.** Alfred picks the category from a list, then one free-text field takes `title :: description`. Chained script filters cost too many round trips for one folder; pure mini-syntax makes the user remember references Alfred could have shown them. **Resolved 2026-09-03 by ticket 06**: the separator is `,` not `::`, split on the first; step 2 is parse-only; the final Return goes to a confirmation screen, not straight to commit.
- **Mutating commands stay backgrounded.** Alfred fires the command, posts a notification immediately, and lets the existing drift markers catch mirror failures later. This is what the CLI already promises, and it is the reason Alfred is faster than the terminal.
- **Alfred replicates both dropped prompts.** Run headless, `add_*` currently skips spell-check silently and takes the offline fallback emoji, because every prompt in the codebase is `isatty`-guarded. Alfred gets its own emoji surface and its own suspect-token confirmation. **Revised 2026-09-03 by ticket 07**: the emoji prompt is no longer a risk. The CLI's Claude emoji call was dropped entirely ([ADR 0002](../../docs/adr/0002-drop-the-claude-emoji-suggester.md)) — `emoji_picker.pick_emoji`, the offline keyword search, is the whole suggester now. So the Alfred emoji surface is a plain offline pick plus manual entry (Alfred's own emoji picker, or a free-text search), with no API call, no latency to hide, and no `ANTHROPIC_API_KEY` to plumb into Alfred's `no-rcs` environment. Spell-check (ticket 08) is the only genuinely interactive prompt left to replicate. **Revised 2026-09-03 by ticket 08**: it is not replicated as a prompt either. Measured at a 1.4 per cent per-title fire rate, it becomes alternate rows on the ticket 06 confirmation screen rather than a step, so the Alfred flow replicates **neither** dropped prompt as a prompt. Nothing in the mutating flow now costs a keystroke it did not cost before.
- **Alfred does the filtering, not aardvark.** One call fetches the whole index on keyword entry; Alfred's own matching filters client-side, instantly, and learns the user's selection order in a way `fd`'s keyword search cannot. **Corrected 2026-09-03**: that matching is **word-prefix**, not true fuzzy subsequence matching, and it applies only in Alfred's "Alfred Filters Results" mode. This assumes the index stays small enough to ship whole, which a prototype must test at realistic scale rather than at today's size.
- **`cd` becomes a terminal handoff, not a reveal.** Alfred cannot change a shell's working directory, so the resolved path opens a new tab in the frontmost iTerm window (falling back to a new window, and to `Terminal.app` for anyone else). Calling this action `cd` in Alfred would be a lie; the glossary needs a name for it.
- **Mirrors are chosen by modifier key.** The CLI opens Craft, Todoist and Drive together; in Alfred, Enter keeps that behaviour and modifiers open one each, plus Finder. This is the single largest gain over the terminal and costs one `mods` block per item.
- **Testing lives in the package.** The real logic — JSON item construction, argument parsing, path discovery — sits in `aardvark_jd/alfred/` where the existing pytest setup reaches it, with the Alfred-invoked entry points kept to a few lines each and excluded from coverage. No AppleScript-driven end-to-end tests of Alfred itself.
- **Errors are results, not exceptions.** A script filter cannot raise, so an error returns a single row carrying the diagnosis. Where a fix is obvious — binary not found, entity not yet synced — Enter on that row performs it.
- **What ships to other people.** The workflow is documented in the README and the docs, and the exported `.alfredworkflow` ships with the package. The `--json` contract is explicitly internal and unstable, so it can be reshaped without a deprecation cycle.

## Decisions so far

<!-- one line per closed ticket -->

- [How is an Alfred 5 workflow authored, and what exactly can a Script Filter return?](issues/01-alfred-workflow-authoring.md): the format is well enough documented to build against, and **Alfred ships first-party template workflows inside its own app bundle** which settle what it actually writes. Four findings constrain the design: Alfred's `PATH` is a documented six entries under `/bin/zsh --no-rcs`, so **no conda, venv, pipx or uv binary is reachable** and the baked-in `sys.executable` is what Alfred's own docs endorse; **configuration defaults live in `info.plist` and user overrides in `prefs.plist`**, which the docs say to gitignore, giving a clean two-layer design; a mod's `variables` **replace** the item's wholesale with no merge, so shared keys repeat in every mod; and `uid` **surrenders result ordering to Alfred** unless paired with `skipknowledge`, with knowledge keyed on the `uid` strings, so the contract needs stable identifiers. Also found: `cache` with `loosereload` (5.5+) addresses the 240 ms cold `fd` directly, one Open URL object can serve all four mirrors via the `alfredworkflow` JSON envelope, and entry points should be **External Scripts** (`type: 8`) with real script files, not inline bodies. **The map's "fuzzy matching" premise was an overstatement and has been corrected above.** The Alfred forum was unreachable (HTTP 403 to every automated fetch), so nothing rests on a forum post.

- [How does a workflow get from a repo directory into Alfred, and stay linked to it?](issues/02-alfred-deployment-mechanics.md): the `user.workflow.<UUID>` directory name is **arbitrary and referenced by nothing** — six installed workflows do not use it at all, and Alfred's scripting dictionary confirms the folder name *is* the workflow UID — so `install_alfred` should create a legible `workflows/aardvark-jd`. **Alfred does not gratuitously rewrite `info.plist`**: two `alfredapp`-authored workflows are byte-for-byte identical to what the vendor committed, after import and use, which is a green light for committing the plist rather than generating it. What it *does* rewrite on edit is narrow and semantic — a **reordered `objects` array** (the real churn risk), `uidata` canvas coordinates, and the `disabled` flag — with zero formatting noise. `.alfredworkflow` is a **zip**, so scripted export is straightforward. Configuration values can be set from outside Alfred by the supported AppleScript `set configuration … in workflow …`. And one trap worth the ticket: `~/Library/Application Support/Alfred/Alfred.alfredpreferences` **also exists on this machine but is vestigial**, so an installer falling back to the default path would write where Alfred never looks and appear to succeed — **the fallback must be a hard failure**. Three questions needing writes into the live preferences folder were deliberately left, and became [Verify what Alfred writes, and whether it follows a symlink](issues/14-verify-alfred-write-behaviour.md). **Resolved 2026-09-04 by ticket 14**: the apparent contradiction was a misread — Alfred writes import-sheet values to `prefs.plist`, not `info.plist`, so the `co.uk` default in the Amazon workflow was vendor-committed, and the two-layer design holds without exception.

- [What is the shape of aardvark's `--json` output?](issues/03-json-output-contract.md): a per-command `[--json]` flag on the nine read/mutating commands plus the three sync commands, never on setup or `cd`. Output is always a versioned object (`aardvark_json: 1`) — `{system, entities}` for reads, `{result}` for mutations, `{error: {kind, message}}` on stdout with a non-zero exit for failures. The **entity record** carries `id` (`"<domain>:<code>"`, the Alfred `uid`, stable across rename/emoji/reindex), `row_key` (numeric index key, for mirror-link correlation), `type`, `domain`, `code`, `title`, `description`, `emoji`, `folder_path`, `archived`, and a `urls` block (`finder`/`craft`/`todoist`/`drive`/`dropbox`, `null` when absent) — every field verified against `db.py`. `fd --json` is flat and in index order; archived entities only under `--json --archived`. `open --json` suppresses opening and returns the record. Mutating results are one uniform shape (`action`, `entity`, `emoji_source`, `corrections`, `sync`, `warnings`). Code lives in one pure `aardvark_jd/json_output.py`, unit-tested; the `print(json.dumps(...))` glue in `cl_utils` is the only coverage-excluded part. Two build notes handed to ticket 13: a new `db.entities_with_links` bulk read, and widening the `add_*`/`set_emoji` worker returns to report emoji provenance and spell corrections.

- [Does the two-step argument entry actually feel right?](issues/06-argument-entry-flow.md): **yes — build the mutating half on the two-step hybrid**, with four corrections from the hands-on run. Separator is **`,`** (comma, split on the first — beats `::`, `/` and the hyphen against real titles). Step 2 shows only the parsed `title = «…»` / `description = «…»` — **no JD code** (it invites typing the code into the title) and no folder path. The final Return **does not commit**: an explicit confirmation screen does. Spell-check (08) and emoji (07) sit **after step 2, before that confirmation** — and `add_id` has **no emoji step**, since IDs carry no emoji. (**Superseded 2026-09-03 by ticket 08**: there is no spell-check step; the order is category → `title, description` → emoji → confirm → run, and the corrections are rows on the confirmation itself.) The flow reads as two prompts, not one — accepted, the speed is the point. Going back to the category list needs an explicit affordance with a visible key hint — handed to ticket 13. The shape stretches to every other mutating command unchanged (`add_project` + a template step, `add_area`/`add_category` + the emoji step, `set_emoji`/`archive` a reference pick plus one field or a confirmation). Prototype on branch `prototype/ticket-06-argument-entry`.

- [Can the emoji suggestion survive being on the interactive path in Alfred?](issues/07-emoji-surface.md): **the question is moot — the Claude emoji call was removed from the CLI entirely** ([ADR 0002](../../docs/adr/0002-drop-the-claude-emoji-suggester.md), branch `feature/drop-claude-emoji-suggester`). `emoji_picker.pick_emoji` — the offline keyword search — is the whole suggester: the default at the interactive prompt, the silent pick non-interactively, `--emoji` to override. This drops the `anthropic` dependency and the `ANTHROPIC_API_KEY` requirement and removes the 15-second worst case. For Alfred that means the emoji surface is a plain offline pick plus manual entry, with no latency to hide and no key to plumb into Alfred's `no-rcs` environment. The ticket-07 prototype's `rerun`/swap-in machinery (branch `prototype/ticket-07-emoji-surface`) is superseded; its finding that Alfred hands a script neither the interpreter path nor the login-shell env survives and feeds tickets 10 and 12. One note to ticket 13: ticket 03's mutating-result `emoji_source` loses its `claude` value.

- [What does the suspect-token confirmation look like in Alfred?](issues/08-spell-check-surface.md): **keep it, but never as a step — it becomes alternate rows on the ticket 06 confirmation screen.** The ticket's premise was wrong: the docstring's 18 per cent is a token-level rate on a synthetic vocabulary, and on 141 real human-typed titles the checker fires on **1.4 per cent** of them, roughly one in seventy, with **zero** true positives and two false ones. So the question became "is something this rare worth a step", and the answer is no — but the check costs 0.002 ms, so a shape that costs no keystrokes is free. "Create as typed" is the **first, default** row; correction rows sit beside it, one per token, each accepted independently; accepting one re-renders the confirmation rather than committing, so Return always means create. Teaching the learned vocabulary now needs its **own explicit modifier** rather than arriving free with a decline, because under this shape declining is the default path and the terminal's rule would teach a word on every reflexive Return — a deliberate divergence from the CLI. Ticket 07 **kept** the emoji step (it removed only the Claude call), so the flows are category → `title, description` → emoji → confirm for `add_area`/`add_category`, and category → `title, description` → confirm for `add_id`. Two notes to ticket 13: detection stays in `spell_check.py`, not `alfred/`; and ticket 03's `corrections` field does **not** serve this screen — `--json` must run detection despite never prompting, and the contract needs *offered* suggestions kept distinct from `corrections`' applied-substitutions meaning. Prototype on branch `prototype/ticket-08-spell-check-surface`. Graduated two CLI-side defects into [Is the spell-checker's tuning wrong?](issues/16-spell-check-tuning.md), which does not block ticket 13.

- [Does shipping the whole index to Alfred hold up at realistic scale?](issues/05-index-payload-and-filtering.md): **yes — ship the whole index.** The plausible lifetime ceiling for a one-person PARA + JD system is ~5,000 entities (categories fill to 15–25 IDs, not 99); ~25,000 is near-full JD population. At 5,000: the Alfred surface feels instant cold, filter latency under 0.5 s, Alfred parse 67 ms; lag first shows at ~15,000. Payload at 5,000: `fd --json` 3.9 MB, Alfred `items` 4.4 MB lean / 6.6 MB fat — mirror URLs a flat ~25% at every scale. Matching (mode "Word matching — Any order", `match` = code + title + path segments) finds a JD ref, a partial-title prefix and a mid-title word; descriptions need folding into `match` (+7%), recommended. `cache` + `loosereload` (`seconds: 3600`) makes the second invocation instant and self-heals a stale cache in the background — a folder from a mutating command shows up one invocation late at worst, which is accepted. No hybrid fallback needed below ~15,000. Two notes to ticket 13: prefer the **lean** payload shape (one `urls` object per item, no per-mod duplication — ~50% smaller, and a modifier resolving from the in-memory index is a cache read not a re-shell); rely on `loosereload` for cache invalidation. Prototype on branch `prototype/ticket-05-index-payload`. Graduated the frecency fog into [Should the Alfred surface rank by frecency, and where does that state live?](issues/15-frecency-and-recall.md).

- [How does the terminal handoff open a tab at the resolved path?](issues/09-terminal-handoff.md): **`open -a "$TERMINAL_APP" "$path"` is the whole handoff — no AppleScript.** The ticket assumed AppleScript, and both handoffs were built and measured before the one-liner was tried; it won on every axis. `osascript` + `quoted form of` does survive every hostile fixture (apostrophe, backslash, `$HOME`, backticks, `&&`, `|`, `"`, emoji, verified by landing directory), but it has one hole — a **newline** in a folder name submits the line early — and `open -a` never builds a shell string, so it has none. It also gives the wanted behaviour anyway: against a running iTerm it opens **a new tab in the existing window**. The three iTerm states dissolve into macOS's problem, which matters because two of them were untestable (these sessions run *inside* iTerm, so quitting it kills the tester). Terminal choice is the `AARDVARK_TERMINAL_APP` configuration variable, else **iTerm when installed, else `Terminal.app`**, a chain that always terminates; `open -a` exits non-zero on a missing app, which is the error row. **Shell integration does not load** in the new tab — a genuine login shell, but the `shell_init` function is absent and `aardvark`/`av` are plain aliases, so `av cd` there prints a path instead of moving. Pre-existing, reproduces in `/bin/bash -lic`, cause now traced into the dotfiles rather than this repo, and ruled out of the map by the user. Costs the Alfred flow nothing, since the handoff sets the directory itself. Finder reveal handed to ticket 13. Recorded traps: `pgrep -x iTerm2` misses the real process name; `running of application` is the one AppleScript property that does not auto-launch. Prototype on branch `prototype/ticket-09-terminal-handoff`.

- [Verify what Alfred writes, and whether it follows a symlink](issues/14-verify-alfred-write-behaviour.md): **the live-editing plan holds and the case for committing `info.plist` got stronger.** Alfred follows a symlinked `workflows/aardvark-jd` completely — loads with no restart, survives quit/relaunch, writes through the link into the repo, and sets a script's working directory to the resolved repo path. Merely opening a workflow in Alfred's editor leaves `info.plist` byte-identical; editing churns only `uidata` coordinates and `objects` order, no semantics and no formatting noise. The import-time configuration sheet writes to `prefs.plist`, **not** `info.plist` — overturning ticket 02's read — so `info.plist` defaults are never rewritten by Alfred and `prefs.plist` (gitignored) holds deltas only. Incidental for ticket 15: `alfred_workflow_data` lives at `~/Library/Application Support/Alfred/Workflow Data/<bundleid>`, outside the synced prefs folder. On dropbox.com the symlink shows as a macOS alias; Dave has ruled cross-machine workflow-dir sync out of scope. Unblocks tickets 04 and 10. Probe artifacts under `prototypes/14-alfred-write-behaviour/`.

- [Is `info.plist` committed, or generated?](issues/04-version-controlling-info-plist.md): **committed, and Alfred's visual editor is the tool that edits it** — the builder option is rejected outright. The decisive enabler is that **every script object is an External Script (`type: 8`) referencing a real file; no body is ever inlined**, which shrinks `info.plist` to structure alone and makes committing it reviewable rather than committing a blob. Tickets 02 and 14 removed every reason for a builder: Alfred's own team commits the plist verbatim, opening a workflow writes nothing, the import sheet writes to `prefs.plist`, and edit churn is confined to two semantics-free regions. Those are contained asymmetrically — **`uidata` is left alone** (stripping it would make Alfred re-lay out the canvas and destroy the editor), while the **`objects` array is sorted by `uid`** by a pure normaliser in `aardvark_jd/alfred/`, exposed as a **`make alfred-normalise` target run manually**, not a git hook (this repo's hooks are unversioned and invisible to others, and an automatic rewrite while Alfred holds the workflow open can lose an edit). The sort rests on one unverified inference — that `objects` order is non-semantic — so **verify it by hand before building the normaliser**, and fall back to a documented reviewer's rule if it fails. **There is no round trip**: ticket 14's symlink means Alfred writes straight into the repo working tree, so the loop is edit in Alfred, normalise, diff, commit, with scripts edited normally outside it. Accepted constraint: the visual editor is authoring-machine-only. Adds `alfred/prefs.plist` to `.gitignore`. Unblocks ticket 10.

- [How does the workflow find aardvark on a second machine?](issues/12-cross-machine-binary-resolution.md): **first-class, because it turned out to be cheap.** The ticket's central worry was unfounded — it feared that using `~/.config/aardvark/` pushes the discovery problem up a level, but that path is fixed and literal, expanded per machine by the shell, created unconditionally on first run and outside Dropbox. No recursion. Resolution is three steps: the **workflow configuration variable** (manual override, syncs), then a **per-machine plain-text pointer file** at `~/.config/aardvark/alfred-binary-path`, then **hard failure**. Two steps were excluded on purpose: a **`PATH` probe** (ticket 01's six entries carry no conda/venv binary, and the rare success is the dangerous one — silently running a different aardvark) and any **plausible-default fallback**. `/usr/local/bin` is on Alfred's `PATH` but is `root:wheel 755`, **verified not writable without sudo**, so the symlink escape was dropped. The pointer holds **one line: the `aardvark` console-script path** — not `sys.executable`, which cannot launch anything with no `__main__.py` — and plain text, not a YAML key, since reading YAML needs the interpreter the file exists to find. Three states are distinguished by `[ -x "$path" ]`: no file (never installed here), dead path (**shown in the row**, because a recorded-but-wrong path is the silent failure the map keeps guarding against), executable (proceed). Enter on either failure row **copies `aardvark install_alfred` to the clipboard** — pre-typing into a terminal would resurrect the AppleScript ticket 09 removed. Version drift of a working-but-old binary is left to ticket 10. Dave confirms the second machine is **hypothetical**, so the failure rows are a guard-rail, not a routine path.

- [What does `aardvark install_alfred` do?](issues/10-install-alfred-command.md): **two separable jobs — always write ticket 12's per-machine pointer file, and deploy the workflow by symlink unless one is already installed by another route.** Two charting decisions were corrected. First, the workflow directory is **`aardvark_jd/resources/alfred/`**, not a top-level `alfred/`: this repo's `MANIFEST.in` and `package-data` would ship the latter in neither sdist nor wheel, and a top-level directory is not importable so runtime location would fall back to `__file__` arithmetic that differs between a checkout and a wheel. Second, `install_alfred` is **not author-only** — the pointer file is needed on every machine, including one that installed the `.alfredworkflow` bundle. The package is installed **editable**, so `importlib.resources` points at the repo here and at site-packages for a package user through one code path: **symlink only, no `--copy`**, target `workflows/aardvark-jd`, and `pip install --upgrade` refreshes the workflow for free. Re-run is idempotent across four target states, and an imported real directory is **never touched**. Version drift is possible only on the imported-bundle route and the workflow detects it itself, comparing `info.plist` `version` against the `--json` `system` version and showing a warning row. The command is **`ADVANCED`** (hidden from `-h`), which is safe only because ticket 12's failure row copies the exact command to the clipboard. Alfred-absent splits into two distinct hard failures — no Alfred at all, versus a present Alfred with an unreadable `prefs.json` — and never falls back to a default path. **`install_alfred --uninstall`** removes the symlink and pointer only, and is the documented removal route because Alfred's own Delete Workflow may delete *through* the symlink into the repo — untested, and graduated into [Does Alfred's Delete Workflow delete through a symlink?](issues/17-alfred-delete-through-symlink.md).

- [What are the Alfred surface's terms called?](issues/11-alfred-glossary.md): **fifteen terms into `CONTEXT.md`, and one existing term sharpened.** The terminal handoff is a **handoff** (`cd` is the shell function that moves the *current* shell; the workflow cannot do that), with **reveal** beside it for Finder, so the mirrors, Finder and the terminal each own one word. Alfred's own terms — `Workflow`, `Script Filter`, `Modifier`, `Keyword`, `Configuration variable` — are **adopted verbatim** in their own `## Alfred's language` section rather than translated, since every Alfred document the reader reaches for uses Alfred's word. The thing itself gets **no proper name**: it is *the aardvark workflow*, the same words in the README, the docs and `install_alfred`'s help. **JSON contract** names ticket 03's shape (short form, "the contract") and **index payload** stays distinct as ticket 05's whole-index fetch, so neither word is overloaded. **Mirror** gains an `_Avoid_` against calling a surface a mirror, and **surface** is defined as a place the system is driven from that holds no copy of the tree — a mirror is synced to and can drift, a surface is neither. Three more terms the prototypes made concrete were named because ticket 13 will lean on each: **confirmation screen**, **binary pointer** and **error row**. Unblocks ticket 13.

- [Should the Alfred surface rank by frecency, and where does that state live?](issues/15-frecency-and-recall.md): **no frecency — index order with `skipknowledge: true` stays, confirming ticket 03's default rather than changing it.** Four reasons, none of them caution. "Recently used" is recorded nowhere, and recording it would make `fd`, `open` and `cd` write back on every invocation — turning the read commands into mutating ones. Any such signal would be **per-machine and unrecoverable**, since the index is unsynced and has no rebuild-from-tree path, so ranking would differ between machines and vanish with the index. Alfred's own learning is **actively wrong here**: `uid` is `<domain>:<code>` and `archive` frees numbers for reuse, so a recycled `A11.10` inherits its predecessor's rank and shows it confidently. And nothing is being fixed — ticket 05 measured that a ref, a title prefix and a mid-title word all find the target. Two candidate signals died on inspection: **`updated_at` is unusable** (written by three functions only, on emoji and rename), and `created_at` is answered better by recall than by ranking. **Recall of a just-created entity comes from the mutating result** (ticket 03 §7), whose record drives a post-create success surface offering reveal, handoff and the mirrors directly — which also covers ticket 05's accepted one-invocation cache lag instead of racing it. Four notes to ticket 13, including that the post-create success surface is now a required part of every mutating flow.

- [Does Alfred's Delete Workflow delete through a symlink?](issues/17-alfred-delete-through-symlink.md): **it unlinks — the data-loss shape does not exist, and it is recoverable besides.** Measured on Alfred 5.7.3 with a disposable workflow symlinked from a scratchpad target outside both the repo and Dropbox: after deleting through Alfred's UI the link was gone from `workflows/` while the target kept its **inode and all five canary hashes**, `nested/deeper/` included — no recursion at any depth. The item in `~/.Trash` **is itself still a symlink**, so an accidental delete is undone by re-running `install_alfred` (idempotent across exactly this state, per ticket 10). The dialog is *not* a mitigation — it says "remove"/"delete", never "Trash", and never mentions the symlink or the real location — which is why this had to be measured rather than assumed. The **Remove Data and Cache folders** checkbox targets `~/Library/Application Support/Alfred/Workflow Data/<bundleid>` and the cache, not the workflow directory. Consequence, taking the ticket's mild branch: `install_alfred --uninstall` stays the documented route **because it also removes ticket 12's binary pointer**, not to protect the working tree; the README states plainly that Alfred's own UI is safe; and ticket 10's conditional bold README warning and `install_alfred` output warning are **not** written. Probe artifacts under `prototypes/17-alfred-delete-through-symlink/`.

- [Is the spell-checker's tuning wrong?](issues/16-spell-check-tuning.md): **yes, in two places — fix the tie-break, move the floor to 5, change no wordlist.** The tie-break fix is free: `suggest` prefers the *shortest* distance-1 candidate, but a dropped letter is the commonest typo and leaves the token shorter than its correction, so the shipped rule picks against the commonest case by construction. Preferring the longest takes right offers 57.6% → **75.0%** and wrong offers 25.0% → **7.6%** with **no change to the fire rate**, since the tie-break decides which candidate is offered, never whether one exists. ("Longest" and "assume a dropped letter" are provably the same rule: at distance 1 the candidate length offsets are exactly `[-1, 0, +1]`.) The floor 6 → 5 takes dropped-letter recall 61.0% → **87.8%** and silence 17.4% → **5.4%**, costing four more suspect tokens on 141 real titles — `ciara`, `lagan`, `macos`, `silla`, all proper nouns the learned vocabulary retires at one dismissal each — for a per-title fire rate of **4.3%** against a stated ceiling of 5%. **Floor 4 is rejected on its own numbers**: identical recall, 12.8% firing. The American-spelling worry was overstated — generating the 1,903 `-ize` twins changes the human-typed corpus not at all and the wide sweep by three tokens, and dismissals are per-token so `normalize` is dismissed once. The docstring's misread-once "18 per cent" is corrected to both rates with their denominators. **This is a CLI change, not an Alfred one**, and ships as its own test-first slice; one note to ticket 13, that the spec should quote 4.3% as the expected fire rate rather than ticket 08's 1.4%. Probe under `prototypes/16-spell-check-tuning/`.

## Not yet specified

- **A direct-keyword layer beside `av`.** Whether one or two daily-driver commands deserve their own top-level keywords, and which. The obvious names (`fd`, `open`) are taken, so any answer needs a prefix scheme. Deliberately deferred: the only honest input is a week of real usage, which does not exist yet.
- **Universal Actions.** Acting on a Finder selection or a selected path from elsewhere in macOS — "file this into aardvark", "which JD code is this folder?". Plausibly the most valuable thing here after the basics, but it is a different input model from the keyword surface and cannot be specified until the keyword surface exists.
- **What happens on a fresh machine.** Installation ordering when the package, the Alfred prefs and the folder tree all arrive by different routes. Narrowed twice on 2026-09-04: Dave has ruled *workflow-directory* cross-machine sync out of scope (ticket 14), so the symlink is authoring-machine-only; and ticket 12 has settled binary resolution, so a fresh machine's failure mode is now a known, legible row rather than an unknown. What remains fog is the *ordering* — what a user should do first when the package, the synced Alfred preferences and the folder tree arrive independently, and whether that sequence needs stating anywhere beyond the README. Thin enough that it may simply fold into ticket 13's documentation section rather than becoming a ticket.

## Out of scope

- **The setup commands** (`init`, `connect_craft`, `connect_todoist`, `connect_dropbox`, `connect_gdrive`, `completion`, `shell_init`). One-time, browser-interactive OAuth flows and one-off token pastes. No worse in a terminal, and an Alfred surface for them would be built once and never used.
- **Polling the drift markers to notify on sync failure.** Attractive, but as a periodic background check rather than as something bolted onto a command's return path — which makes it a different feature with a different trigger, past this map's destination.
- **End-to-end tests that drive Alfred itself via AppleScript.** Slow, flaky, and they test Alfred rather than this code.
- **Cross-machine sync of the workflow directory.** The `install_alfred` symlink into Alfred's prefs folder is an authoring-machine convenience; on dropbox.com it materialises as a macOS alias, and what a second machine's Alfred makes of it is not a question this effort answers. Ruled out by Dave 2026-09-04 while resolving [ticket 14](issues/14-verify-alfred-write-behaviour.md). Binary resolution on a second machine stays in scope as ticket 12.
- **A stable, public `--json` API.** Documenting the contract as public would prevent reshaping it the first time the workflow needs a new field. Internal and unstable until it has settled in use.
